# The Six That Don't Exist — Replacement Repos Audit

**Date:** 2026-11-11. **Status:** audit only — no code copied, no dependencies added, nothing pushed by this audit.

**Question Eric asked:** audit the replacements for the six blueprint names that do not exist, the same way as the earlier batches — for each, find out what code we can USE, what has to be ADJUSTED to use, what we can't use and can only take INSPIRATION from and rebuild ourselves, and what to DEFER or DROP.

**Answer in one paragraph:** of the 7 replacement repos audited (6 names, 7 repos — Mojo-LLM has two candidates), **none is a USE and none is an ADJUST**. Three are DEFER (hydro-project/infinity, dorjeduck/llm.mojo, a2ui-project/a2ui) and four are DROP (resitkurttr/mojo-llm, SciAgent/OpenDCAI, NuMojo for its blueprint slot, spine-tools/SpineOpt.jl). The useful yield is entirely inspiration: the RAP hibernation pattern from Infinity, the MAX `linalg.matmul` variant from llm.mojo, and the temporal/stochastic/Benders patterns from SpineOpt — all to be rebuilt as original START code, none to be copied or depended on now. The recurring finding holds again: coupling is the barrier, not licence — with one exception (a2ui), where the barrier is neither licence nor coupling but a missing consumer.

## Method

- **Starting point:** the repo triage (`~/workspace/v032-review/blueprint-triage/REPO_TRIAGE.md`) and the full 70-candidate borrowing sweep (`ALL_CANDIDATES_BORROWING_PLAN.md`), which named these replacements as follow-ups and dropped the six blueprint names.
- **Workers:** seven subagents, one per repo, each reading the real source (shallow git clone or the GitHub connector) — README, top-level structure, core module(s) for the claimed role, and the LICENSE file. Their per-repo findings are in `source-audit/replacements/<name>/` (JSON + reasoning note). The coordinator read all seven evidence files in full before writing this report.
- **Line counts are approximate and the counting basis varies** (Rust `*.rs` only, `.mojo` package only, newline count over a whole tree, raw `wc -l`). They are good enough to judge size and coupling; they are not a precise census. Each JSON records exactly how its count was made.
- **Classification counts:** USE 0, ADJUST 0, INSPIRATION-REBUILD 0 (as a primary classification — three repos carry inspiration takeaways as a secondary verdict, listed below), DEFER 3, DROP 4. Total 7. Shallow (depth-1 clone, source read but not exhaustively) 3: resitkurttr/mojo-llm, SpineOpt.jl, a2ui-project/a2ui. None was README-only.

## Governance filter (applied to every candidate)

- **v0.3.2 allocation:** Python — orchestration, memory, governance, self-edit; Julia — planning contracts and domain logic; Rust — constraint and verification kernels; PyTorch/Python — neural work; Mojo only on demonstrated need.
- **Trust boundaries:** Planning / Evaluation / Verification / Governance / Execution must not collapse. A borrowed piece must not let a planner certify its own output, or turn unverified data into verified.
- **Wire format stays JSON** — never pickle from an untrusted source.
- **Every result needs_human_decision=true.** Verified still means PASS *and* human approval.
- **No new paid dependencies/services without Eric's approval.**
- **Licence verified per source.** Flags that stand: SpineOpt.jl GPL-3.0 LICENSE file vs LGPL-3.0-or-later README/headers (copyleft either way, contradiction unresolved); NuMojo imports `parallelize` from `max.algorithm` (MAX-coupled, not stdlib-only); llm.mojo also imports `parallelize` from `max.algorithm` (portions under the MAX License); resitkurttr/mojo-llm's Python scraper has no licence field per source and no robots mention.

## Per-candidate sections

### 1. hydro-project/infinity — DEFER (Module 1)

**Licence:** Apache-2.0, verified from `LICENSE.txt` (full text), plus `NOTICE` (Copyright 2026 Hydro Contributors; initial developer of some parts is Amazon Web Services). Each crate declares `license = "Apache-2.0"`. **Stars:** 809, forks 94. **Last commit:** `e1a3e4b`, 2026-11-06. Created 2026-04-13, 515 commits, 56 open issues, not archived. **Lines:** 57,969 — `wc -l` over all 169 `*.rs` files under `crates/` (depth-1 clone at `e1a3e4b`); excludes the TS agent side (3,927 lines) and docs. **Depth:** full.

**What it is:** a Rust workspace (21 crates) for massively concurrent LLM-agent systems. `infinity-agent-core` (15,372 lines; `event_processor.rs` alone 5,209) is the agent loop; `infinity-agent-lambda` (1,894 lines) is the AWS Lambda deployment; `rap-protocol`/`rap-client` define RAP, an async tool protocol with MCP compatibility; `sandbox-*` (9,347 lines) sandbox coding-agent work in git/jj worktrees; `infinity-provider-protocol` defines the `ModelProvider` trait (the runtime never calls an LLM directly) with Bedrock and rig backends.

**Blueprint claim vs reality (Module 1):** async process loops TRUE (yield-while-waiting, hibernate-as-pure-data, wake on event); scale-to-zero TRUE but AWS-bound (Lambda + DynamoDB/SQS/Scheduler/DSQL; the local runtime exists but local scale-to-zero is just process exit); Wasm sandboxing FALSE (zero hits for wasm/wasmtime/wasmer anywhere in `crates/` — sandboxing is git/jj worktrees plus optional macOS `sandbox-exec` / Linux `bwrap` for the coding agent's builds/tests, not a language-runtime sandbox); polyglot memory mapping FALSE (zero hits for mmap/shared-memory/polyglot anywhere). 2 of 4 Module 1 claims hold; the two that make it distinctive for START do not exist.

**Paid-LLM warning confirmed:** the README example wires `StaticModel` to `global.anthropic.claude-sonnet-4-6` via Bedrock, live tests use the same model, and the rig bridge adds OpenAI/Gemini. It is the *default shape*, not hard-wired — the `ModelProvider` trait (1,280 lines, with a channel-based mock model for tests) means a local provider is architecturally possible, but none ships in-tree.

**Why DEFER, and why coupling is the barrier:** licence is clean; copying would be legally fine. The barriers are coupling: 57,969 lines across 21 interlocked crates for a small hibernation idea; AWS coupling for the scale-to-zero story; paid-LLM default; and an autonomous agent loop with **no** governance hooks — no `needs_human_decision`, no verified/unverified distinction, no approval gate — in the wrong language for the v0.3.2 allocation (orchestration is Python; Rust is for constraint/verification kernels). Adopting the loop as-is would collapse Planning/Execution and let a planner certify its own output.

**Smallest copyable unit, if one were ever wanted:** `crates/rap-protocol/src/lib.rs` (392 lines, `RapInvocation`/`RapCallback` JSON types) — **not** recommended for copying now: `ToolCallId` semantics are provider-controlled (Bedrock `tooluse_*` IDs), callback URLs carry no auth/verification field, and it drags RAP's anyone-holding-a-callback-URL-can-deliver-a-result trust model into START.

**What to take instead:** the RAP hibernation pattern as **inspiration to rebuild originally** — fire-and-forget tool invocation, immediate HTTP 200 ack, runtime persists state and exits, result delivered later to a callback URL; subscriptions persist across hibernations. Wire format is JSON (`serde_json`) — compatible with START's JSON-only rule. Rebuild as original START code (small JSON envelope + hibernate/wake state machine in the Python orchestration layer) with `needs_human_decision=true` and a verified flag added — neither exists in RAP.

**Per-file verdicts:** USE none; ADJUST none as a whole; DEFER `infinity-agent-core` (loop/system), `infinity-agent-lambda`, `rap-protocol` (as dependency/copy), `infinity-provider-protocol` (trait shape only, as inspiration); INSPIRATION-REBUILD the RAP spec docs (15 files) + hibernation pattern and the provider-trait boundary shape for START's own Python provider boundary; DROP `infinity-provider-bedrock`, `infinity-provider-rig` (paid APIs), the daemon/CLI/Slack/CDK product surface, and `sandbox-*` for the Module 1 Wasm claim.

**Unblocks:** (1) a local, non-paid `ModelProvider` for START; (2) governance hooks designed and wrapped around it; (3) scale-to-zero demonstrated without AWS; (4) if the Lambda/AWS path is ever wanted, Eric explicitly approves the AWS dependency.

### 2. resitkurttr/mojo-llm — DROP (Module 3)

**Licence:** MIT, verified from the repo's own `LICENSE` file (Copyright (c) 2026 Reşit Kurt); GitHub API agrees (spdx_id MIT). Licence is **not** the barrier. **Stars:** 0, forks 0. Created 2026-07-19, last commit/push 2026-07-23 (`cfe2dff`) — about 4 days of activity, inactive since, single author. **Lines:** 5,457 — `wc -l` over all 34 files in the shallow clone (excl. `.git`): Mojo 3,888 (main.mojo 905 + src/ 2,903 + tests/ 80), Python 1,280, other 289. Non-blank/non-comment Mojo: 3,190. **Depth:** shallow (depth-1 clone, 1 commit visible) — README, all source files, LICENSE read in full; key functions read, not just README.

**Reasoning:** the blueprint's "Mojo-LLM" does not exist as named, and this candidate does not fill the gap. The triage note ("single-file inference script, 0 stars, no autograd") is right in substance even though the repo has grown to 17 `.mojo` files: the extras are unintegrated fragments, not a system. There are **zero cross-module imports anywhere** in `src/` or `tests/` — `main.mojo` is self-contained, `src/` modules reference types they never define, and the tests use types they never import.

**It is not training code.** The word "train" occurs zero times in the entire repo, as do gradient, backprop, autograd, optimizer, and loss. `self_learning.mojo` keeps a list of past outputs and returns canned suggestion strings; no weight is ever updated.

**It is barely inference code either.** Weights are deterministic pseudo-random values (`Vector.random`/`Matrix.random` use `(i*7+13)%100` arithmetic, not an RNG), no weight loading exists on any CLI path, the BPE merges list is always empty (no merges file is ever loaded — tokenize degrades to per-codepoint tokens with per-process ids), sampling uses a fixed threshold `r = 0.42` instead of randomness, timings are hardcoded `0.0`, and attention degenerates (`n_heads = d_model`, so `head_dim = 1`).

**Most of `src/` is stubs.** `web_browser.mojo` returns placeholder text ("Page content for \<url\>", "real HTTP will be done with the Mojo OS module"); `api_server.mojo` has no HTTP server and returns the canned string "API response for: \<model\>"; `save_load.mojo:validate_checksum()` always returns `True` (marked `# Placeholder`); `gguf.mojo` parses only magic/version/tensor-count and never reads metadata or tensors; the tests are non-runnable as shipped (no imports; `build.sh` has the test calls commented out).

**Governance fails twice.** `verification.mojo` is heuristic self-scoring (word overlap, sentence-length variance, default score 0.7, valid at 0.6) — a model certifying its own output, collapsing Verification into Execution with no human decision and no verified/unverified distinction. The Python pipeline is a scraper with UA rotation and referer spoofing ("browsing without leaving a fingerprint") over 28 Turkish sources with no licence field per source and zero mentions of licence/copyright/robots anywhere in `python/` — it violates START's data rules outright.

**Mojo version:** README requires ≥ 0.26.2; the code is 0.26-era (`UnsafePointer` backing, `^` move syntax, pre-1.0 spellings). Whether it compiles on START's Mojo 1.2.0 was not run-tested in this shallow audit — but there is nothing worth porting anyway.

**Coupling, not licence, is the barrier** — the licence is permissive MIT; the repo is fragmented, stub-filled, and functionally empty for Module 3. **Smallest copyable unit: none.** The closest-to-real piece, the tile-based online-softmax loop in `flash_attention.mojo`, is a standard textbook algorithm and is uncompilable as written (it uses `Matrix`, defined only in `main.mojo`, with no import). If START ever wants Mojo flash-attention, it should be written originally against its own types.

**Verdict: DROP.** Do not revisit unless upstream gains a real training loop and a runnable, tested package.

### 3. dorjeduck/llm.mojo — DEFER (Module 3)

**Licence:** MIT, verified from the `LICENSE` file (Copyright (c) 2024 Martin Dudek); README also states MIT — no licence barrier. **Stars:** 382, forks 17. Created 2024-04-13, last commit 2026-10-04 (commit `95674f6`, "TinyStories: preserve shard order; fix script name in usage docs"). **Lines:** 7,073 — `wc -l` over the 7 code files in a depth-1 clone: train_gpt2.mojo 1,951, train_gpt2.py 588, test_gpt2.mojo 284, prepro_tinyshakespeare.py 82, prepro_tinystories.py 124, variants/train_gpt2_v1_linalg_fwd.mojo 2,011, variants/train_gpt2_v2_linalg_fwdbwd.mojo 2,033; total 7,073 including blank lines and comments; code-only 5,299. The variants are near-full copies of the baseline, so unique Mojo code is roughly the baseline + test file (~2,235 lines total, ~1,665 code-only). **Depth:** full.

**What it is:** a real, substantial repo — a Mojo port of Karpathy's llm.c (2024 snapshot, `train_gpt2.c @ 2d43e5b`) that trains GPT-2 124M on CPU. **This is training code, not inference-only:** `train_gpt2.mojo` has hand-written forward/backward kernels (encoder, layernorm, matmul, attention, GELU, residual, softmax, cross-entropy), an AdamW update, a `DataLoader`, a BPE `Tokenizer`, and a 41-step training loop with validation-loss checks and sampling-based generation as a sanity check. `test_gpt2.mojo` checks forward-pass logits/loss and 10 Adam steps against PyTorch reference values. `train_gpt2.py` is Karpathy's own reference script, used to export the `gpt2_124M.bin` checkpoint the Mojo program loads.

**Why DEFER, not USE:** (1) **No demonstrated need.** Under the v0.3.2 allocation, neural work is PyTorch/Python and Mojo is only for demonstrated need. START already has MiniGPT in PyTorch and 25 original Mojo programs including custom transformer layers. A Mojo GPT-2 trainer duplicates MiniGPT's role in a language where START has no training pipeline. (2) **Mojo-version unproven.** `pixi.toml` pins Mojo 1.0.0 / max 26.5.0; START uses Mojo 1.2.0. The changelog shows every Mojo release broke this code (24.3 → 24.4 → 24.5 → 24.6 → 25.4 → 25.5 → 1.0.0b2 → 1.0.0 each needed updates). Running on 1.2.0 needs a try-compile, not an assumption. (3) **Coupling, not licence, is the barrier.** One 1,951-line monolith (kernels + model + dataloader + tokenizer + loop), variants are near-full copies, and it needs an external `gpt2_124M.bin` checkpoint and tokenised datasets. Smallest copyable unit would be a single kernel (e.g. `matmul_forward`, ~41 lines) — but START already has original Mojo transformer code, so there is nothing to copy. (4) **Narrow scope.** CPU-only fp32, GPT-2 124M only, hardcoded 41-step demo loop, ~150 tok/s baseline; README says "no concrete plans to develop the project further" and points to ulmentflam/llm.mojo for GPU work.

**What is worth keeping in mind:** the V2 variant (`variants/train_gpt2_v2_linalg_fwdbwd.mojo`) claims **7.44× throughput (1,109 vs 149 tok/s)** from swapping forward+backward matmuls to MAX `linalg.matmul` — the strongest single design datum in the repo for any future Mojo training work. The port-test pattern in `test_gpt2.mojo` (check against PyTorch reference values with a tolerance) is a good test-design template. Adjacent licence flag, not a blocker: the code imports `parallelize` from `max.algorithm`, so running it pulls the `max` package, portions of which are under the MAX License.

**Comparison with resitkurttr/mojo-llm:** dorjeduck is clearly the better of the two. resitkurttr has 0 stars, is inference-only, no autograd, no training. dorjeduck has real training, a PyTorch-reference test harness, and maintenance through Mojo 1.0.0. Neither is a USE for START right now.

**Unblocks:** only if Eric demonstrates a Mojo training need, plus a successful try-compile on Mojo 1.2.0.

### 5. Mojo-Numerics-and-Algorithms-group/NuMojo — DROP (Module 15)

### 6. spine-tools/SpineOpt.jl — DROP (Module 18)

**Licence:** LGPL-3.0-or-later per the README.md "License" section and the LGPL header in every source file read — **BUT the `LICENSE` file itself contains the full GPL-3.0 text**, `LICENSE.LESSER` contains LGPL-3.0, and the GitHub API reports GPL-3.0. Copyleft either way, with an upstream contradiction that makes even a small copy unsafe to attribute. **Copyleft = dependency only, never copy.** Its dependency SpineInterface.jl is also reported GPL-3.0 by the API (9 stars). **Stars:** 82 (matches triage), forks 24, open issues 141. **Last commit:** 2026-11-04 (`6512a32e`, "Add VRE modelling and an example system to the renewable targets how-to (#1420)"); API `pushed_at` is 2026-11-10 (a later push on some other ref; HEAD date used). **Lines:** 23,225 in `src/` (154 `.jl` files, raw `wc -l`, no blank/comment stripping); all `.jl` in the repo including tests: 41,684 (test/ alone 17,659 lines, 27 files). Breakdown: constraints 7,663; data_structure 4,086; variables 2,390; objective 943; util 696. **Depth:** shallow (depth-1 clone) but **not README-only**: README, Project.toml, LICENSE, LICENSE.LESSER, `src/SpineOpt.jl`, `src/run_spineopt.jl`, `src/run_spineopt_basic.jl`, `constraint_nodal_balance.jl`, `total_costs.jl`, `benders.jl`, `temporal_structure.jl` read in full; full `src/` tree listed.

**What it actually is:** a large, mature, actively maintained **energy-system** optimisation framework — not a generic planning engine and not a JuMP replacement. It is a JuMP **application**: `Project.toml` requires JuMP `^1.23.5` and HiGHS `1`; `run_spineopt(url_in, url_out)` builds a `JuMP.Model` from the SpineOpt template, adds ~60 constraint files and ~16 objective cost terms, solves, and writes results back to a Spine database. Extras over bare JuMP: pre-built unit/node/connection energy formulation, investment + stochastic + rolling-horizon machinery, Benders decomposition, MGA (Modelling-to-Generate-Alternatives), Monte Carlo, forced-outage generation, and a v0.x→v1.x DB migration chain.

**Verdict vs JuMP (already assembled: JuMP 1.32.1 + HiGHS 1.26.1, canonical julia-current/):** **redundant and heavier for the same job.** SpineOpt adds nothing START needs at the solver layer — it consumes JuMP. What it adds is all energy-domain content plus the Spine DB data layer, and neither transfers to START's generic multi-sector planning (current synthetic spine is food/agriculture: wheat/potato, 600 t delivered / 50 t shortage). Forcing an energy ontology (unit_flow, node_state, gas pressure, voltage angle) onto non-energy sectors would be a modelling error, not reuse. START's planning-search already has its own MCTS + independent JuMP+HiGHS LP cross-check — the verification pattern SpineOpt lacks.

**Why DROP, in order:** (1) **Wrong scope:** energy-only, not multi-sector. Module 18's role is generic integrated planning. (2) **Redundant:** JuMP+HiGHS already assembled and canonical; SpineOpt is a layer on top of it. (3) **Data model fights the wire format:** native I/O is a Spine database (SQLite, `sqlite:///` URLs); the JSON in `examples/` is Spine-DB export JSON, not START's flat JSON. Adoption means building a Spine-DB↔JSON adapter plus template/migration machinery. (4) **Dependency weight:** 17 deps incl. SpineInterface 1 (separate repo, itself declaring PyCall, MetaGraphsNext, Graphs, JSON…), Arrow, Distributions, Graphs, MetaGraphsNext — the whole Spine stack for a data layer START does not use. (PyCall is a *declared* dep in SpineInterface's Project.toml; its runtime use was not verified in this audit.) (5) **Licence:** copyleft + GPL/LGPL contradiction (above). (6) **Governance:** `run_spineopt()` builds, solves and writes results in one call — Planning/Evaluation/Execution collapse, no separate Verification, no `needs_human_decision`, no verified/unverified distinction. It would let a planner certify its own output.

**Coupling vs licence:** both are barriers, but **coupling is the operative one for the DROP verdict and licence for the no-copy verdict**. Even with a permissive licence, SpineOpt would still be dropped for Module 18: every file assumes SpineInterface parameters, the SpineOpt template and the Spine DB — nothing is separable, and its domain does not match multi-sector planning. Licence is why nothing can be copied.

**Smallest copyable unit: none.** Copyleft bars copying, and no file is extractable standalone anyway (all constraint/variable files assume the template data structures, `@fetch` macros and SpineInterface `Parameter` machinery).

**Inspiration-rebuild only (patterns, no code):** `src/data_structure/temporal_structure.jl` — rolling-horizon / representative-period time slices (TimeSliceSet, model windows); `src/data_structure/stochastic_structure.jl` — stochastic scenario/path structure; `src/benders.jl` — Benders master/subproblem split with objective-upperbound cuts, only inside START's existing verify-then-approve flow; `src/constraints/constraint_nodal_balance.jl` — nodal balance equation pattern (injection + in − out, sense ≥/=/≤), generalises to any flow-conservation constraint; `run_spineopt_mga.jl` / `run_spineopt_hsj_mga.jl` — Modelling-to-Generate-Alternatives as a way to surface near-optimal alternatives for human choice.

**Reconsideration conditions (all four required):** (1) START gains a dedicated energy-sector module; (2) upstream resolves the GPL-3.0 LICENSE file vs LGPL-3.0-or-later README/headers contradiction; (3) a Spine-DB↔START-JSON adapter is built; (4) the monolithic run is split so a separate verify step and human approval gate sit between planning and any accepted result.

### 7. a2ui-project/a2ui — DEFER (Module 25)

**Licence:** Apache-2.0, verified from the root `LICENSE` file (227 lines: full Apache 2.0 text, plus an MIT appendix covering only the bundled third-party file `eval/bin/transcrypt`; Dart sub-packages carry their own Apache-2.0 LICENSE files). **Stars:** 17,055, forks 1,378. Created 2025-09-24, 1,897 commits. **Last commit:** `24d1bf9`, 2026-11-11 — "feat!: emit @-prefixed v1.0 component envelope keys across spec and SDKs (#4044)". **Lines:** 1,648,072 — newline count over every git-tracked file in a depth-1 clone at HEAD `24d1bf9`, excluding `.git` and the two lockfiles (yarn.lock, uv.lock): 4,726 files. Breakdown: specification 49,723 / 307 files; python 132,694 / 392 (of which 366 `.py` files = 128,017 lines); typescript 241,108 / 1,262; swift 68,540 / 279; kotlin 10,669 / 54; dart 150,048 / 503; docs 354,691 / 213; samples 207,841 / 784; conformance 79,296 / 228; eval 196,636 / 336; catalogs 9,202 / 56; blueprints 7,184 / 31; tools 111,562 / 136. The total is inflated by docs media (29 MB demo mp4, 15 MB mp4, 8.8 MB gif) and multi-MB `.diff` history files under `eval/iterative_format_optimizer/history/`. Focused numbers that matter for START: v1.0 JSON schemas `specification/v1_0/json/*.json` = 1,217 lines in 12 files; `specification/*.md` v1.0 docs are part of the 49,723 specification lines. **Depth:** shallow (depth-1 clone, full tree read).

**What it actually is:** the blueprint's "A2UI Engine" does not exist. The real repo is the **A2UI protocol**: a JSON-based streaming UI specification (v1.0 current; v0.9.1/v0.9 previous; v0.8 deprecated, per `specification/versions.json`) plus agent SDKs and native renderers in five languages. It is a wire format plus libraries, not a runtime engine. Google-originated, large, active, and heavily starred — the opposite of the six missing names. The wire format is JSON throughout (compatible with START's JSON wire format): four agent→renderer messages (`createSurface`, `updateComponents`, `updateDataModel`, `deleteSurface`) plus bidirectional typed RPC in v1.0 (`callRendererFunction` / `callAgentFunction` + responses), verified against runtime catalog definitions. What it does: lets an agent stream UI as validated JSON data to a native renderer (React, Lit, Angular, Flutter, SwiftUI, Jetpack Compose) that builds the interface from a strict component catalog, so the agent composes interfaces without executing code or touching host-app capabilities it was not granted.

**Why DEFER, not USE:** the barrier is neither licence nor coupling — this is the one audit so far where the recurring question gets "neither". Licence is Apache-2.0. Coupling is low by design: JSON messages over any transport, and the Python core's only dependencies are small permissive libraries (pydantic, jsonschema, babel, referencing, regex). The barrier is a **missing consumer:** (1) START has no user-facing UI surface and no renderer. The renderers are TypeScript (React/Lit/Angular), Dart/Flutter, SwiftUI and Kotlin/Jetpack Compose — none of that is in the v0.3.2 allocation, which has no UI language at all. Adopting the agent SDK now would emit messages nobody renders. (2) v1.0 is still churning: HEAD today (2026-11-11) is a *breaking* envelope change (`@`-prefixed v1.0 component keys), while the published PyPI packages (a2ui-core 0.6.0, a2ui-agent-sdk 0.11.0) predate it. Pin and verify the published core speaks v1.0 before depending on it. Unblocked by: Eric approving Module 25 UI work and picking a renderer stack, plus confirming a published a2ui-core that supports v1.0.

**Per-file verdicts:** **USE as dependency (when unblocked):** `a2ui-core` (PyPI 0.6.0) and `a2ui-agent-sdk` (PyPI 0.11.0) — Python, fits the orchestration allocation. No paid service in either. `a2ui-adk` (google-adk/google-genai) is a separate optional package: do not adopt without Eric's approval. **Smallest copyable unit:** `specification/v1_0/json/agent_to_renderer.json`, 220 lines; minimal useful set is 3 files / 909 lines (plus `common_types.json` 391 and `catalog_definition.json` 298); all 12 v1.0 schemas are 1,217 lines. Apache-2.0, copyable with notice — but copying now with no consumer would be dead weight, so the copy itself is deferred with the adoption. **REWRITE (original START code):** the emitter/adapter that turns verified plans into surfaces; the human-approval gate for consequential function calls; any renderer/host app. **DEFER:** all renderers, `a2ui-a2a`/`a2ui-adk`, conformance/eval tooling. **DROP:** only the name "A2UI Engine". Nothing in the repo is dropped on licence or relevance grounds.

**Governance fit — the real gap:** A2UI's security model is genuinely good and aligned with START's boundaries: UI as data, not code; strict schema validation; per-function execution boundaries (`rendererOnly` / `agentOnly` / `rendererOrAgent`); `requiresUserActivation` gating functions like `openUrl` behind a user gesture, with such functions forced to `rendererOnly` so the agent cannot invoke them remotely. What it does **not** have is any verification or human-approval concept. In the v1.0 spec, "verify" means schema/tree-integrity validation and boundary checks. There is no `needs_human_decision`, no verified/unverified distinction, no approval workflow. START must add all of it on top: emit surfaces only for plans that are verified PASS *and* human-approved, gate consequential function calls behind approval, and stamp the verification status onto every surface — because a slick rendered surface can make an unverified plan *look* verified, and that is exactly how a planner would certify its own output through the presentation layer.

**Scale note:** the repo totals 1,648,072 lines across 4,726 tracked files, but that number is inflated by docs media and multi-MB `.diff` history files. The part START needs is tiny: 1,217 lines of JSON schemas plus two PyPI packages. Do not vendor the repo.
